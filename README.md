# Rancho alarm

One Python 3.11+ asyncio service for Raspberry Pi OS Lite, managed by systemd.
One checkout at `/home/tim/rancho`, one uv-managed venv, no deployment copies.
Logs go to stdout/stderr and are captured by journald; no file logging.

## Step 1 scope

This is a runnable skeleton, **not a functioning alarm**. It loads configuration,
starts a Telegram placeholder, waits for SIGINT/SIGTERM, and shuts down cleanly.
It does not poll Telegram, contact cameras, touch GPIO, persist/restore state,
or send alerts. Do not connect a siren expecting this skeleton to make it safe.

```text
/home/tim/rancho/
  .env                   # local secrets/configuration; gitignored
  .env.example           # tracked template without secrets
  state.json             # future persistent armed state; gitignored
  .venv/                 # uv-managed; gitignored
  pyproject.toml
  uv.lock                # generated by uv; tracked
  deploy/rancho.service  # tracked; symlinked into /etc/systemd/system/
  src/rancho/
    __main__.py          # configuration, logging, asyncio entry point
    app.py               # composition and shutdown
    core/
      config.py          # reads .env from the working directory
      state.py           # state types; no persistence yet
      events.py          # in-process broadcast queues
      hardware.py        # hardware protocols; no drivers
    frontends/
      telegram.py        # lifecycle placeholder; no requests
```

The core does not import front ends. A future web UI can use the same core.
Event queues are unbounded for now; choose a backpressure policy before using
them for continuous camera events.

`.env` is loaded directly by Python, without shell expansion. Relative state paths
are resolved against its directory. The default is `state.json` next to `.env`.
**No state file is written or restored yet**; the skeleton starts disarmed.

## First setup on the Pi

Run as `tim` on `rancho`. These instructions assume the checkout is at
`/home/tim/rancho` on the Pi, on a filesystem available at boot. If you choose a
different user/path, update the unit and symlink command accordingly.
No commands have been executed by the coding agent.

### 1. Install Python and uv

```sh
cd /home/tim/rancho
sudo apt-get update
sudo apt-get install -y python3 curl ca-certificates
python3 --version
curl -LsSf https://astral.sh/uv/install.sh -o /tmp/rancho-install-uv.sh
UV_INSTALL_DIR="$HOME/.local/bin" sh /tmp/rancho-install-uv.sh
sudo install -m 0755 "$HOME/.local/bin/uv" /usr/local/bin/uv
uv --version
```

Expect apt/installer output, `Python 3.11.x` or newer, and a uv version.
If uv is already installed and on PATH, skip its installation commands.

### 2. Prepare local configuration and the venv

```sh
cd /home/tim/rancho
if [ ! -e .env ]; then cp .env.example .env; fi
chmod 600 .env
uv sync --python /usr/bin/python3 --no-python-downloads
```

Existing `.env` contents are preserved. Blank Telegram settings are sufficient
for Step 1. Edit secrets in `.env`, never in `.env.example`.

Expect uv to create `.venv`, generate `uv.lock` if absent, and install the project,
`python-dotenv`, Taskipy, and dependencies. Taskipy is in the default `dev` group.
The lockfile should stay with the project; the agent has not generated it.

The project is installed in **editable mode**, so the service uses source directly
from this checkout. Run uv as `tim`, not with sudo. Systemd runs the venv's Python
directly, so starting/restarting never resolves or downloads dependencies.

### 3. Link and start the service

```sh
sudo ln -sfn /home/tim/rancho/deploy/rancho.service /etc/systemd/system/rancho.service
sudo systemctl daemon-reload
sudo systemctl enable --now rancho.service
sudo systemctl status rancho.service --no-pager
sudo journalctl -u rancho.service -n 20 --no-pager
```

Expect `active (running)` and journal lines like:

```text
INFO rancho.frontends.telegram: Telegram placeholder: polling and messaging are not implemented
INFO rancho.app: Rancho started (skeleton; mode=disarmed; no hardware access or state persistence)
```

If status is failed or restarting, inspect the journal before continuing.
The service runs as `tim`, with `/home/tim/rancho` as its working directory.
Journald retention follows the Pi's existing configuration, including volatile
storage. There is no separate service account or `/var/lib/rancho` requirement.

### 4. Verify the restart task

```sh
cd /home/tim/rancho
uv run --frozen --no-sync task restart
sudo systemctl is-active rancho.service
sudo journalctl -u rancho.service -n 15 --no-pager
```

Expect `active`, shutdown messages (`Rancho stopping`, `Telegram placeholder
stopped`, `Rancho stopped`), then startup messages again. Taskipy invokes
`sudo systemctl restart rancho.service` and may request your sudo password.
`--no-sync` avoids modifying the environment; `--frozen` avoids updating the lockfile.
`Restart=always` handles unexpected exits; an explicit systemctl stop still stops it.

## Deploy an update

```sh
cd /home/tim/rancho
git pull
uv sync --locked
uv run --frozen --no-sync task restart
```

Expect a Git update (or already-up-to-date message), uv install/audit output, and
a service restart. `--locked` rejects a lockfile out of date with `pyproject.toml`.
After changing dependencies yourself, run `uv lock` to update the lockfile first.
For source-only edits made directly on the Pi, only the restart is needed.

After changing `deploy/rancho.service`, run this before the restart:

```sh
sudo systemctl daemon-reload
```

The symlink points directly at the tracked unit, so no copying is needed. `.env`,
state, and the venv stay local and are not tracked. Never delete the checkout as
part of a deploy. GPIO permissions, relay polarity, and physical boot/crash safety
remain for the hardware implementation step.
